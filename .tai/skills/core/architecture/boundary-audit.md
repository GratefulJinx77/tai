# Skill: Boundary Audit## TriggerArchitect wants to verify service separation and module boundary enforcement across the codebase.## Pre-conditions- Boundary rules defined in `.tai/context/boundaries.md`- Source files exist and are organized into modules or services## Steps1. Read `.tai/context/boundaries.md` to load the current boundary rules.2. Scan all source files in the project for import/require statements.3. Build an import graph: map each file to the modules it imports from.4. For each import, classify it as:   - **Internal** (within the same module/service) — allowed   - **Cross-boundary** — check against boundary rules   - **External** (third-party package) — allowed unless restricted5. Identify all boundary violations: cross-boundary imports that are not permitted by the rules.6. Identify near-violations: imports that are technically allowed but are close to a boundary (e.g., importing from a shared module that is tightly coupled to another service).7. Check for new modules or directories that do not yet have boundary rules defined.8. Recommend boundary rule additions for any new modules found.9. Generate a boundary audit report:   - Total files scanned   - Violations found (with file, line, and the rule violated)   - Near-violations flagged   - New modules without rules   - Recommended rule additions10. Log skill completion to `.tai/telemetry/sessions.jsonl`.## Verification Gate- [ ] All source files have been scanned for imports- [ ] All violations are identified with file, line, and rule reference- [ ] Near-violations are flagged separately from hard violations- [ ] Boundary rules are up to date for all existing modules- [ ] Audit report is generated
